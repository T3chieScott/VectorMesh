# VectorMesh — Add Operations Scope Management for API Tokens

You are working on the existing VectorMesh application.

The Display Operations API has already been implemented and correctly authenticates existing `vm_...` API tokens.

Current verified behaviour:

- A valid API token successfully authenticates against existing token-enabled endpoints such as:

  `GET /api/screens`

- The same valid token currently receives:

  `403 FORBIDDEN`

  from:

  `GET /api/operations/projects`

  because it has not yet been granted the required Operations scopes.

The relational Operations permission model already exists using:

- `token_operations_scopes`
- `user_operations_scopes`

The missing piece is a safe admin workflow for assigning and removing Operations scopes on API tokens.

## Objective

Extend the existing API Tokens management UI so an authorised administrator can view and manage Operations scopes for each API token.

Do not change the existing token authentication mechanism.

Do not recreate the Operations permission model.

Do not add a parallel scope system.

Reuse the existing `token_operations_scopes` table and existing scope constants/middleware.

---

# 1. API Token Scope UI

Locate the existing VectorMesh API Tokens administration page.

For each token, add an Operations Permissions / Operations Scopes section.

The administrator should be able to see and manage the supported scopes.

Current scopes include:

- `operations.view`
- `operations.screen.read`
- `operations.multiview`
- `operations.diagnostics.read`

Future scopes already defined or anticipated may include:

- `operations.player.refresh`
- `operations.player.restart`
- `operations.player.reboot`
- `operations.logs.read`
- `operations.content.control`

Do not expose future scopes in the UI unless they already exist in the shared scope definition and are considered safe to grant.

The UI must derive its available scope list from the shared Operations scope definitions wherever practical, rather than duplicating hard-coded strings.

---

# 2. Human-Friendly Labels

Do not show only raw scope strings.

Display clear names and short descriptions.

Example:

### View Projects & Venues
`operations.view`

Allows discovery of accessible projects and venues.

### Read Screens
`operations.screen.read`

Allows listing screens and reading safe screen status information.

### Multiview
`operations.multiview`

Allows creation of read-only monitor sessions.

### Read Diagnostics
`operations.diagnostics.read`

Allows access to operational diagnostics where implemented.

The raw scope string may appear as secondary text for technical clarity.

---

# 3. Recommended Multiview Preset

Add a convenient preset/action:

**Grant Multiview Access**

This should grant exactly:

- `operations.view`
- `operations.screen.read`
- `operations.multiview`

It must NOT automatically grant:

- diagnostics
- reboot
- restart
- refresh
- logs
- content control

This preset is intended for the VectorMesh Multiview Electron application and should follow least-privilege principles.

Also provide:

**Remove Multiview Access**

which removes those three scopes only.

Do not remove unrelated scopes that may also be assigned to the token.

---

# 4. Scope Editing Behaviour

The administrator must be able to:

- view current scopes
- grant individual scopes
- revoke individual scopes
- apply the Multiview preset
- remove the Multiview preset

Changes should take effect immediately on subsequent API requests.

Do not require token regeneration when scopes change.

Do not display or expose the raw API token again merely to edit permissions.

---

# 5. Backend Endpoints

If suitable endpoints do not already exist, add admin-only endpoints for reading and updating token Operations scopes.

Preferred shape:

`GET /api/admin/api-tokens/:tokenId/operations-scopes`

Response:

```json
{
  "tokenId": "token-uuid",
  "scopes": [
    "operations.view",
    "operations.screen.read",
    "operations.multiview"
  ]
}
```

For updates, either use:

`PUT /api/admin/api-tokens/:tokenId/operations-scopes`

with:

```json
{
  "scopes": [
    "operations.view",
    "operations.screen.read",
    "operations.multiview"
  ]
}
```

or reuse an existing admin API pattern if the application already has a better convention.

Prefer replacing the full set atomically rather than sending many small grant/revoke requests, unless the existing backend architecture strongly favours individual mutations.

---

# 6. Authorisation

Only appropriately privileged users may change API-token scopes.

At minimum:

- Admin users: allowed
- Account Managers: allowed only if this matches the existing API-token management permissions and tenant boundaries
- Site Users: not allowed

Follow the application's existing API-token ownership/tenant rules.

An administrator must never be able to grant scopes to a token belonging to another tenant/account unless they already have legitimate cross-tenant administrative authority.

---

# 7. Tenant Safety

Scope editing must preserve the token's existing tenant/account boundaries.

Granting:

`operations.view`

must NOT broaden which projects the token can see.

The token should continue to have access only to resources allowed by its owning account/user/tenant context.

Scopes control **what operations are permitted**, not **which tenant data becomes visible**.

This distinction is critical.

---

# 8. Validation

Only known Operations scopes may be stored.

Reject:

- unknown scope strings
- malformed values
- duplicate scopes where relevant

Use the central Operations scope definition as the source of truth.

Return:

`400 BAD_REQUEST`

for invalid scope values.

---

# 9. Database Behaviour

Reuse:

`token_operations_scopes`

Do not add another table unless absolutely necessary.

When replacing a token's scope set, perform the operation transactionally if possible:

1. validate requested scopes
2. remove scopes no longer present
3. add newly granted scopes
4. commit

Do not create duplicate rows.

Respect any existing unique constraints.

---

# 10. Audit Logging

Scope changes should be audited.

Record at minimum:

- administrator user ID
- target token ID
- scopes added
- scopes removed
- timestamp

Do NOT log:

- raw API token
- token secret/hash
- monitor tokens

Use the existing audit/activity logging system.

Suggested event types:

- `api_token.operations_scopes.updated`
- `api_token.multiview_access.granted`
- `api_token.multiview_access.removed`

Use the existing audit naming convention if one already exists.
