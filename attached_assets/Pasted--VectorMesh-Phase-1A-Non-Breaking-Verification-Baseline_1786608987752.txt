# Dual-environment compatibility — mandatory

VectorMesh operates in two separate environments:

1. **Development and testing:** Replit, using Replit’s development database, Secrets, workflows and preview URL.
2. **Production:** An externally hosted Linux server, using its own PostgreSQL database, environment variables, persistent media storage, public domain, reverse proxy and process manager.

The Replit environment itself is not transferred to production. The tested Git source and the output from `npm run build` are transferred and deployed to the hosted server.

The repository and production build must remain portable between both environments.

A successful Replit test does not prove production compatibility by itself. Any proposed change must be checked for both environments.

## Production compatibility rules

Do not:

- Add Replit-only runtime dependencies to application or production code.
- Require Replit integrations, Replit database objects or Replit URLs in production.
- Hard-code Replit domains, `localhost`, `127.0.0.1`, development ports or local filesystem paths into application code.
- Rename, remove or change the meaning of existing environment variables.
- Change `APP_URL` or existing public URL resolution.
- Change media URLs, monitor URLs, API routes or callback URLs.
- Change the production build command.
- Change the production build output entry point.
- Change the production start command.
- Change PostgreSQL schema, migrations or production data.
- Change upload paths, stored media paths or persistent-storage behaviour.
- Change session, cookie, HTTPS, host or reverse-proxy behaviour.
- Replace environment-based secrets with values stored in source control.
- Run tests, migrations, schema pushes or cleanup operations against production.
- Introduce assumptions that only work inside Replit.

Preserve:

- `npm run build`
- Production entry point `dist/index.cjs`
- `NODE_ENV=production`
- Existing `DATABASE_URL` contract
- Existing `SESSION_SECRET` contract
- Existing `APP_URL` contract
- Existing `UPLOAD_DIR` contract
- Existing SMTP environment-variable contracts
- Existing external-integration environment-variable contracts
- Existing relative API and media URL behaviour
- Existing reverse-proxy compatibility
- Existing PostgreSQL compatibility
- Existing persistent upload-directory layout
- Existing Replit development workflows
- Existing hosted-server deployment workflow

All database-backed verification must use the Replit development database or a disposable test database.

Before running any database-backed test:

- Establish that `DATABASE_URL` is not the production database.
- Do not print the database URL or credentials.
- Do not reveal the database password, hostname or connection string in logs or the report.
- If the database cannot safely be identified as non-production, stop and report the blocker.
