Digital Signage System (Onsite) — Replit Build Brief

0) Goal

Build an onsite digital signage platform for a conference & exhibition centre, supporting:
	•	Up to 50 meeting-room screens (mixed sizes/aspect ratios)
	•	6 indoor public screens
	•	2 external LED walls (custom rasters)
	•	Mixed media: JPEG/PNG, MP4, GIF (converted to MP4), plus HTML widgets
	•	Overlays/tickers: weather, clock, date, custom text, client logos
	•	Multi-client branding (client/event separation)
	•	Timelines + scheduling (programme blocks)
	•	Live override mode (temporary takeovers)
	•	Local server + Raspberry Pi display nodes
	•	Reliable fallback behaviour and diagnostics

No booking integration required.

⸻

1) Operating Model (How users use it)

Roles
	•	System Admin (venue ops)
	•	Content Editor (event team)
	•	Viewer (read-only)

Tenancy / Branding
	•	Tenant = Venue (single)
	•	Clients = organisations hiring the venue
	•	Events = dated programmes per client
	•	Brand Pack = theme assets per event (logo sets, colours, fonts, defaults)

Workflow
	1.	Create Client
	2.	Create Event under Client (select or create Brand Pack)
	3.	Create Layout Templates (base + optional profile overrides)
	4.	Upload media (scoped to event/client)
	5.	Build Programme:
	•	schedule blocks by date/time/day-of-week
	•	assign layouts & playlists per screen group
	6.	Publish Programme version
	7.	Players pull and cache everything
	8.	Optional Live Override to take control temporarily
	9.	Diagnostics to confirm health + what’s playing

⸻

2) MVP Deliverables (must have)

A) Admin Web App (CMS)
	1.	Authentication + RBAC
	2.	Client / Event management
	3.	Brand Pack editor:
	•	primary/secondary colours
	•	fonts (name + fallback)
	•	logo uploads (light/dark)
	•	default background image/video (optional)
	•	default standby slate configuration
	4.	Screen management:
	•	register screen/player with a pairing code
	•	name, location, tags
	•	assign Display Profile (resolution, orientation)
	•	assign Screen Group(s)
	5.	Display Profiles:
	•	width, height, refresh target (optional)
	•	safe area padding
	•	type: standard / LED wall
	6.	Media Library:
	•	upload JPEG/PNG/MP4/GIF
	•	on upload: extract metadata (dimensions, duration, codec)
	•	convert GIF → MP4 rendition (FFmpeg)
	•	generate thumbnails
	•	store checksum (sha256)
	•	tagging (event/client scope)
	7.	Layout Templates (zone-based):
	•	define zones (main, ticker, clock, logo strip, html region)
	•	zone positioning via percentage + anchors
	•	optional per-profile overrides (for odd aspect ratios)
	8.	Programme builder:
	•	create programme for an event
	•	create Schedule Blocks with:
	•	targets (screen groups / individual screens)
	•	time rules (date range, days of week, start/end time)
	•	layout template selection
	•	zone sources:
	•	playlist (media rotation)
	•	widget (weather/clock/date/html)
	•	priority
	•	Programme Versions:
	•	draft vs published
	•	publish creates immutable version
	•	rollback to previous version
	9.	Live Override:
	•	take over a screen/group immediately
	•	select layout + content
	•	set expiry (absolute time or duration)
	•	auto revert
	•	audit log
	10.	Diagnostics dashboard:

	•	screen online/offline, last heartbeat
	•	current programme/version + current item
	•	cache status/missing assets
	•	device info (model, temp, storage, uptime)
	•	errors in last 24h

B) Player (Raspberry Pi) App
	1.	Pairing/registration:
	•	show pairing code on first boot
	2.	Content sync:
	•	pull assigned programme/layout + brand pack
	•	download all required assets
	•	validate checksums
	•	cache locally
	3.	Playback engine:
	•	render layout zones full-screen
	•	play images/videos in main zone
	•	overlay ticker/clock/date/logo/html widgets
	•	support “contain/cover” rules per zone
	4.	Fallback behaviour:
	•	if server unreachable: keep playing last known good cached programme
	•	if cache missing/invalid: display standby slate (branded)
	•	if video fails: skip + log error; fallback to standby if repeated failures
	5.	Telemetry:
	•	heartbeat every 10–30s (configurable)
	•	report current content, errors, temp, storage, uptime
	6.	Local diagnostics page (on the Pi):
	•	device details, network info, assigned screen ID
	•	last sync time
	•	current playing item
	•	buttons: restart player, clear cache, reboot

	•	Offline “export event package”
	•	Alert routing (email/Teams webhook)
	•	Multi-server redundancy (primary/secondary)

4) Recommended Stack (Replit-friendly)

Server
	•	Node.js + TypeScript
	•	API: Fastify or NestJS (either is fine)
	•	DB: PostgreSQL
	•	ORM: Prisma
	•	Storage:
	•	local filesystem for MVP (/data/assets)
	•	optional MinIO later
	•	Transcoding: FFmpeg on server

Admin UI
	•	Next.js (React) + TypeScript
	•	Auth: simple JWT + refresh tokens (or NextAuth if you prefer)

Player
	•	Option 1 (recommended MVP): Electron is heavy on Pi; avoid.
	•	Option 2 (recommended): Chromium kiosk + local player web app:
	•	small Node “agent” service on Pi
	•	local web app renders signage (HTML5 video + Canvas/DOM overlays)
	•	agent handles sync + telemetry
	•	Use systemd to run the agent + watchdog

5) Deployment Model

Development (Replit)
	•	Run API + Admin UI + DB in Replit for rapid iteration
	•	Provide a “Player Simulator” page in Admin UI that emulates a screen in-browser

Production (Venue LAN)
	•	Deploy server onsite using Docker Compose:
	•	api
	•	web
	•	postgres
	•	optional nginx reverse proxy
	•	Players point to onsite server via static IP/DNS

6) Core Data Model (Prisma-level entities)

Minimum set:

Auth
	•	User(id, email, passwordHash, role, tenantId)
	•	AuditLog(id, userId, action, entityType, entityId, timestamp, payload)

Tenancy
	•	Tenant(id, name)
	•	Client(id, tenantId, name)
	•	Event(id, clientId, name, startDate, endDate, brandPackId)

Branding
	•	BrandPack(id, eventId or clientId scope, name, version, colors, fonts, logoAssets[], defaultStandbyConfig)

Screens
	•	DisplayProfile(id, name, width, height, orientation, safePadding, type)

Content

Programmes

Telemetry

7) API Endpoints (first cut)

Auth
	•	POST /auth/login
	•	POST /auth/refresh
	•	POST /auth/logout

Screens
	•	POST /screens/pair (pairingCode -> screenId)
	•	GET /screens/:id/config (player pulls assigned profile + current event context)
	•	POST /screens/:id/heartbeat
	•	GET /screens/:id/diagnostics

Sync
	•	GET /players/:screenId/manifest
	•	returns: published programme version, required assets + checksums, brand pack, layout templates
	•	POST /players/:screenId/reportDownload (optional)

CMS
	•	CRUD: clients, events, brandpacks, displayProfiles, screens, groups
	•	CRUD: media upload (multipart), list/search, tags
	•	CRUD: layout templates
	•	CRUD: programmes + versions + blocks
	•	CRUD: live overrides

⸻

8) Player Sync Manifest (contract)

A single manifest response should be enough for the player to operate offline:

Manifest includes:
	•	screenId, displayProfile
	•	activeEventId
	•	activeProgrammeVersionId
	•	brandPack (resolved, with logo asset refs)
	•	layoutTemplates (resolved versions)
	•	scheduleBlocks (resolved)
	•	assets list:
	•	assetId
	•	best rendition path for this profile
	•	checksum
	•	file size
	•	fallbackStandby configuration

Player logic:
	•	download missing/changed assets by checksum
	•	keep previous cache until new one is complete
	•	switch atomically to new published version

⸻

9) Rendering Rules (player)

Zones support types:
	•	MEDIA (playlist rotation)
	•	TICKER (text + optional weather)
	•	CLOCK (time/date formatting)
	•	LOGO (static or rotating set)
	•	HTML (trusted snippets or hosted page, sandboxed)

Scaling per zone:
	•	contain / cover
	•	background fill (solid or blurred image)
	•	safe area padding

Ticker:
	•	left-to-right scroll
	•	supports multiple items (separator)
	•	can include icons (weather)

⸻

10) Weather / Time widgets
	•	Time/date: local device time (with timezone config)
	•	Weather:
	•	For MVP: server fetches and caches weather (so players don’t need internet)
	•	Provide location config per venue (or per screen group)

(If you later need per-city/per-campus, extend to multiple locations.)

⸻

11) Non-functional requirements
	•	Works without internet once onsite
	•	Player continues operating if server is down
	•	No cross-client asset leakage
	•	All published versions are immutable and rollback-able
	•	Audit log for live overrides + publishing
	•	Basic security:
	•	per-player API key / token
	•	TLS inside venue optional but recommended

13) Acceptance Criteria for MVP
	•	Can create a client/event with brand pack
	•	Can register 3–5 screens with different display profiles
	•	Can create a programme with at least 2 schedule blocks
	•	Screens show:
	•	images + videos
	•	ticker + clock + logo overlay
	•	Publish + players update within 30 seconds
	•	Live override works and expires back to programme
	•	If server is unplugged, players keep playing cached content
	•	Diagnostics shows accurate online/offline and current content
