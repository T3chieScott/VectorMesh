# VectorMesh — Unify Player and Monitor Rendering for Pixel-Accurate Multiview

## What & Why

VectorMesh Multiview is now successfully discovering projects/screens, creating monitor sessions, rendering test patterns, and displaying Canvas/composite screens.

The remaining major problem is visual fidelity.

For an engineer, Multiview is only useful if the monitor tile accurately represents what the physical VectorMesh player is rendering.

We have confirmed that some HTML/layout content currently renders differently in Monitor mode than on the real player.

Observed symptoms include:

- incorrect scaling
- HTML elements positioned differently
- responsive layouts reflowing inside the smaller monitor viewport
- incorrect cropping / apparent zoom
- content looking different from the physical display
- Canvas rendering now works, but the broader rendering architecture still appears to contain duplicated or divergent logic

The architectural requirement is therefore:

> Player mode and Monitor mode must use the same visual rendering pipeline and the same logical screen coordinate system.

The difference between Player and Monitor must be limited to physical-device capabilities and side effects.

Do not implement a collection of one-off CSS fixes for Monitor mode.

Do not create monitor-specific approximations of player content.

---

# Core Rendering Principle

The configured physical display profile defines the logical rendering surface.

Example:

Physical display profile:

1920 × 1080

The shared VectorMesh renderer should always render onto a logical:

1920 × 1080

surface.

For Multiview, that completed logical surface is then uniformly scaled down to fit whatever monitor tile is available.

Correct:

1920×1080 logical screen
        ↓
shared VectorMesh renderer
        ↓
exact physical-player visual result
        ↓
scale entire result to fit
        ↓
500×281 Multiview preview

Incorrect:

500×281 Electron/browser viewport
        ↓
HTML/CSS responds to 500×281
        ↓
layout reflows
        ↓
different result from physical player

Responsive HTML must see the physical screen dimensions, not the Multiview tile dimensions.

# Phase 3 — Create Shared Rendering Model

Refactor Player and Monitor so both consume the same shared render model.

Preferred architecture:

Content Resolver
       ↓
Screen Render Model
       ↓
Shared Screen Renderer
      ↙          ↘
 Player Host    Monitor Host

The shared render model should contain everything required to reproduce the physical screen visually.

Conceptually:

{
  logicalWidth,
  logicalHeight,
  profile,
  layout,
  zones,
  media,
  playlists,
  fonts,
  playerVars,
  screen,
  client,
  event,
  canvas,
  testPattern,
  liveOverride
}

The exact structure should follow the current application architecture.

Avoid duplicating calculations between player.tsx and monitor components.

---

# Phase 4 — Shared Screen Renderer

Player and Monitor must ultimately render through the same screen-rendering component/component tree.

If there are currently separate implementations such as:

PlayerLayoutRenderer
MonitorLayoutRenderer

or duplicated zone/Canvas/viewport calculations, refactor them into shared components/services.

The goal is:

Player:
<PlayerHost>
    <SharedScreenRenderer renderModel={...} />
</PlayerHost>

Monitor:
<MonitorHost>
    <SharedScreenRenderer renderModel={...} />
</MonitorHost>

Names are illustrative only.

Do not force this exact React structure if the codebase already has a better abstraction.

# PlayerCapabilities Remain Separate

Monitor mode must remain read-only.

Preserve the existing deny-by-default PlayerCapabilities behaviour.

Physical Player:

- canHeartbeat = true
- canReportHealth = true
- canPair = true
- canPersistDeviceIdentity = true
- playerCommandsEnabled = true

Monitor:

- canHeartbeat = false
- canReportHealth = false
- canPair = false
- canPersistDeviceIdentity = false
- playerCommandsEnabled = false

These differences must not alter visual rendering.

Rendering must not branch on mode unless there is a genuinely unavoidable visual reason.

---

# Logical Screen Surface

Introduce or reuse a shared logical screen surface.

For a 1920×1080 profile, the renderer should behave as if it has a fixed 1920×1080 viewport regardless of the actual browser/Electron tile size.

The monitor page should create something conceptually like:

<div class="monitor-viewport">
  <div
    class="logical-screen"
    style="
      width: 1920px;
      height: 1080px;
      transform: scale(...);
      transform-origin: top left;
    "
  >
     SHARED SCREEN RENDERER
  </div>
</div>

The scale factor should be:

min(
  availableMonitorWidth / logicalWidth,
  availableMonitorHeight / logicalHeight
)

Preserve the original aspect ratio.

Letterboxing/pillarboxing is acceptable and preferable to reflowing the physical-screen layout.

Do not stretch independently in X and Y.

---

# HTML / Web Content

Pay particular attention to HTML/web content.

Any HTML or iframe content should believe it is running at the physical screen resolution.

For a 1920×1080 screen:

- iframe logical size should be 1920×1080 where appropriate
- CSS media queries should evaluate as they do on the physical player
- responsive sites must not see the Multiview tile dimensions
- playerVars and injected variables must be identical
- base URLs and asset paths must be identical
- font loading must match
- sandbox attributes must match unless Monitor security specifically requires otherwise
- devicePixelRatio differences should not change layout geometry

If iframe/web content currently receives the real monitor tile dimensions, correct this using the shared logical screen model rather than monitor-specific CSS hacks.

---

# Canvas / Composite Screens

Canvas screens have recently been enabled in Monitor mode.

Verify that the Canvas implementation now uses the shared logical renderer.

Do not keep a separate copied Canvas geometry calculation inside Monitor.

Shared Canvas logic must determine:

- overall canvas dimensions
- physical viewport dimensions
- canvasX
- canvasY
- crop/translation
- clipping

Both Player and Monitor should consume the same resulting geometry.

# Performance

Do not implement screenshot streaming or server-side video encoding.

The Monitor page should still render live content locally in Chromium.

The shared logical rendering surface may be scaled visually using CSS transforms or an equivalent efficient browser mechanism.

Avoid unnecessary duplicate React trees or off-screen full-resolution copies where possible.

---

# Security

Do not weaken Monitor security to achieve visual parity.

Monitor must still never receive:

- physical device token
- pairing code
- physical-player secret
- writable player identity

Shared rendering means shared visual logic, not shared credentials or physical-device privileges.
