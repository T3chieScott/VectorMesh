Apply these final technical corrections to Task #330 before implementation. They refine the existing design and do not expand its functional scope.

1. **The monitor-session cookie must itself be cryptographically unforgeable.**

Do not authenticate a monitor session using only a `monitorSessionId` stored in a cookie.

After successful bootstrap exchange, either use the application's existing securely signed/encrypted server-side session mechanism or generate a second independent cryptographically random monitor-session secret.

Preferred model:

- bootstrap token: 32-byte random value, single-use
- monitor session cookie secret: separate 32-byte random value
- store only SHA-256 hash of the monitor cookie secret server-side
- cookie contains the raw random secret plus any non-secret session identifier required for lookup
- cookie is Secure, HttpOnly, SameSite=Strict, scoped appropriately to monitor routes
- knowledge or guessing of `monitorSessionId` alone must never authenticate a monitor session

Update the `monitor_sessions` schema if necessary to include a `sessionSecretHash` or equivalent.

2. **Remove the requirement to guarantee identical response timing.**

For invalid, expired, revoked and already-used monitor credentials:

- return the same generic HTTP 401 response
- use the same response body/error code
- do not disclose why authentication failed
- do not leak token/session state through logs or error messages

Do not claim exact timing equality across database and application execution paths.

3. **Correct the invariant test flow.**

Because the bootstrap token is single-use, the invariant test should:

- record all physical-player state before monitoring
- create one monitor session
- perform bootstrap exchange once
- establish the monitor-session cookie
- load and reload the canonical tokenless `/monitor/:screenId` page multiple times using that established monitor session
- optionally exercise content polling/rendering multiple times
- assert afterwards that physical-player state is unchanged

Maintain a separate test proving that reuse of the original bootstrap token returns 401.

If testing multiple complete bootstrap flows, create a fresh monitor session/token for each flow.

4. **Simplify the Multiview integration documentation.**

Do not require Electron to use a hidden WebContentsView for bootstrap.

The intended workflow should be:

`view.webContents.loadURL(monitorUrl)`

Chromium should naturally:

- request the bootstrap URL
- receive the HttpOnly cookie
- follow the HTTP 302
- arrive at the canonical tokenless `/monitor/:screenId` page

The same WebContentsView should then remain the live monitor view.

5. **Clarify revocation semantics.**

Setting `revokedAt` must immediately make all existing credentials/cookies associated with that monitor session unusable on the server.

The system does not need to remotely delete an existing browser's cookie at the moment of revocation. Clear it when practical on subsequent requests, but server-side authorisation must reject it immediately regardless of whether the browser still stores it.

6. **Clarify expiry audit semantics.**

Do not require code execution exactly when `expiresAt` is reached.

Record expiry when an expired session is encountered during authentication and/or when the cleanup process identifies/removes expired sessions. Document the chosen behaviour.

All other #329 and #330 requirements remain unchanged.
