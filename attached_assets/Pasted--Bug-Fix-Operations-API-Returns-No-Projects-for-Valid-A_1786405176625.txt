# Bug Fix — Operations API Returns No Projects for Valid API Tokens

We have identified a production bug in the Display Operations API.

## Verified behaviour

A valid `vm_...` API token:

- authenticates successfully
- has the required `operations.view` scope
- successfully accesses the existing API:

`GET /api/screens`

and receives the expected screens belonging to the token's tenant/account.

However:

`GET /api/operations/projects`

with exactly the same Bearer token returns:

```json
[]
```

with HTTP 200.

This means authentication and Operations scope authorisation are working, but project/tenant visibility resolution for API-token-authenticated requests is not.

## Likely cause

Task #329 specified that `/api/operations/projects` should use `storage.getUserClientIds` to determine accessible projects.

That logic may assume a normal authenticated session user and may not correctly resolve accessible client/project IDs when the request was authenticated using a `vm_...` API token.

Do not assume this is definitely the cause. Trace the request and prove the cause before modifying code.

## Required behaviour

A `vm_...` token must inherit the same tenant/project visibility it already has on the existing token-enabled API.

If a token can access screens belonging to project/account X through `/api/screens`, the Operations API must expose the corresponding project through:

`GET /api/operations/projects`

provided the token also has `operations.view`.

Operations scopes determine **what actions the token can perform**.

The token's existing tenant/account association determines **which data it can see**.

These two concepts must remain separate.

## Investigation

Trace:

1. Bearer-token authentication in `isAuthenticatedOrToken`.
2. What request properties are populated when authentication is via:
   - human session
   - API token
3. How the token's owner/account/tenant/client access is represented.
4. How `/api/screens` determines which records the same API token may access.
5. How `/api/operations/projects` currently determines accessible projects.
6. `storage.getUserClientIds` and whether it expects a real user ID/session.
7. Whether subsequent Operations endpoints have the same issue:
   - `/api/operations/projects/:projectId/venues`
   - `/api/operations/venues/:venueId/screens`
   - `/api/operations/screens/:screenId`
   - monitor-session creation

Do not implement a one-off fix only for `/projects` if the underlying token access-context abstraction is wrong.

## Preferred architectural fix

Introduce or reuse a single access-context abstraction that can resolve tenant/project access regardless of authentication method.

Conceptually:

```ts
interface OperationsAccessContext {
  authType: 'session' | 'api-token';
  userId?: string;
  tokenId?: string;
  accountId?: string;
  accessibleProjectIds: string[];
}
```

The exact implementation should follow the existing VectorMesh architecture.

Both session users and API tokens should feed into the same downstream Operations access checks.

Do not make individual route handlers guess whether `req.user` or `req.apiToken` exists.

## Critical security requirements

Do NOT:

- grant a token broader tenant access simply because it has `operations.view`
- make `operations.view` equivalent to global project access
- bypass tenant checks for API tokens
- treat API tokens as admins
- expose projects belonging to another tenant/account
- change existing Bearer-token authentication semantics

A token must see only the projects permitted by its existing owning user/account/tenant context.

## Expected result

Using the existing valid Multiview token:

```bash
curl \
  -H "Authorization: Bearer vm_REDACTED" \
  https://vectormesh.4wallcloud.com/api/operations/projects
```

should return the projects associated with that token's existing VectorMesh tenant access rather than:

```json
[]
```

For example:

```json
[
  {
    "id": "...",
    "name": "...",
    "status": "...",
    "startDate": null,
    "endDate": null
  }
]
```

## End-to-end validation

After fixing project discovery, test the complete token-driven Multiview chain using the same token:

1. `GET /api/screens` → existing authorised screens
2. `GET /api/operations/projects` → authorised projects
3. `GET /api/operations/projects/:projectId/venues` → authorised venues
4. `GET /api/operations/venues/:venueId/screens` → authorised screens
5. `GET /api/operations/screens/:screenId` → authorised screen summary
6. `POST /api/operations/screens/:screenId/monitor-session` → successful monitor session for an authorised screen

Also prove:

- project belonging to another tenant → 403
- venue belonging to another tenant → 403
- screen belonging to another tenant → 403
- monitor session for another tenant's screen → 403
- removing `operations.view` still causes project discovery → 403
- removing `operations.multiview` still causes monitor-session creation → 403

## Regression tests

Add tests specifically covering API-token authentication, not just session users:

- valid scoped API token receives its own projects
- valid scoped API token does not receive another tenant's projects
- project → venue → screen discovery works end-to-end using a Bearer token
- monitor-session creation works using the same Bearer token
- session-user behaviour remains unchanged

Before changing code, report the precise root cause.

Then implement the smallest architectural fix that resolves token tenant/access context consistently across the whole Operations API.

At completion report:

- files changed
- access-context approach used
- tests added
