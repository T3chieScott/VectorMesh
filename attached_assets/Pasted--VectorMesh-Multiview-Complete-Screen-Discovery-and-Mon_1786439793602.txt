# VectorMesh Multiview — Complete Screen Discovery and Monitor Rendering

We have now completed live end-to-end testing of the VectorMesh Multiview application against the Operations API and identified three production gaps.

These are backend / monitor-runtime issues. Do not implement workarounds in the Electron application.

## Issue 1 — Ungrouped Screens Are Missing

Current Multiview discovery works by:

Project
→ Screen Groups
→ Screens in each group
→ merge/deduplicate

This means any screen belonging to the project but not assigned to a screen group is completely absent from Multiview.

This is now verified in production.

### Required fix

Add:

`GET /api/operations/projects/:projectId/screens`

Required scope:

`operations.screen.read`

The endpoint must return **every screen belonging to the selected project**, regardless of whether the screen belongs to:

- zero groups
- one group
- multiple groups

Return the existing safe Operations screen envelope plus group membership.

Example:

```json
[
  {
    "id": "screen-001",
    "name": "Main Entrance LED",
    "status": {
      "online": true,
      "lastHeartbeat": "..."
    },
    "display": {
      "width": 1920,
      "height": 1080
    },
    "player": {
      "hostname": "...",
      "ipAddress": "...",
      "hardwareClass": "..."
    },
    "groups": [
      {
        "id": "group-001",
        "name": "Hall 1"
      }
    ]
  },
  {
    "id": "screen-002",
    "name": "Ungrouped Screen",
    "status": {
      "online": false,
      "lastHeartbeat": null
    },
    "display": {
      "width": 1920,
      "height": 1080
    },
    "player": {
      "hostname": null,
      "ipAddress": null,
      "hardwareClass": null
    },
    "groups": []
  }
]
```

Do not expose:

- deviceToken
- pairingCode
- monitor credentials
- internal secrets

The same tenant/access rules as the existing Operations endpoints must apply.

This endpoint should become the preferred Multiview discovery route.

Do not remove the existing group-specific screen endpoint.

# Issue 2 — Test Pattern Does Not Render Correctly in Monitor Mode

Verified production behaviour:

A screen configured to display the VectorMesh test pattern shows only:

`Test Pattern`

inside Multiview rather than displaying the actual test-pattern graphic rendered by the physical player.

This indicates monitor mode is not going through the same rendering component/content path as player mode for test-pattern content.

### Required behaviour

Monitor mode must render the same visible test pattern as the physical player.

Do not duplicate the test-pattern implementation.

Reuse the existing player test-pattern renderer/component.

PlayerCapabilities must continue to disable all physical-player side effects.

Monitor mode must still NOT:

- heartbeat
- report health
- pair
- persist device identity
- send player commands

This task changes rendering only.

Add a regression test or component-level test proving that:

physical player test-pattern state
and
monitor test-pattern state

resolve to the same visual/render model.

# Issue 3 — Canvas / Composite Screens Are Explicitly Unsupported

Verified production behaviour in the EY GPG Barcelona project:

Every screen that belongs to a Canvas / multi-display wall shows:

`Canvas composite screen - multi display wall screens are not supported in monitor mode.`

This is not acceptable for Multiview.

Canvas screens are a core VectorMesh display type and must be monitorable.

### Required behaviour

A monitor session represents an individual physical VectorMesh screen.

If that screen belongs to a larger Canvas/composite display, monitor mode must render the exact content region that physical screen is configured to display.

Reuse the existing physical-player Canvas rendering/cropping/transform logic.

Do not build a separate approximate Canvas renderer for Multiview.

For example, if a Canvas is:

5760 × 1080

with three physical 1920 × 1080 screens:

Screen A:
canvasX = 0

Screen B:
canvasX = 1920

Screen C:
canvasX = 3840

then each monitor session must show the appropriate individual 1920×1080 crop exactly as the corresponding physical player does.

The same applies vertically and to arbitrary canvas dimensions/positions.

Respect existing fields such as:

- canvasEnabled
- canvasWidth
- canvasHeight
- canvasX
- canvasY
- canvasGroupId

and any other existing canvas/display-profile transformation logic already used by the real player.

### Critical architecture requirement

Do not duplicate Canvas calculations inside the monitor route.

Extract/reuse a shared rendering configuration/resolver if necessary so:

`player mode`

and

`monitor mode`

consume the same calculated screen viewport/render configuration.

The only difference between modes should remain runtime capabilities / side effects.

---

# Shared Rendering Principle

The long-term rule should be:

> If the physical VectorMesh player can render it, monitor mode should be able to render the same visible output unless there is an explicit security reason not to.

Monitor mode is not a simplified content preview.

It is a read-only representation of the real screen.

The shared path should support:

- normal layouts
- playlists
- scheduled content
- test patterns
- fallback layouts/content
- Canvas/composite screens
- portrait/landscape profiles
- web content
- video/images
- other existing player-renderable content

while PlayerCapabilities prevents monitor sessions from acting as physical players.
