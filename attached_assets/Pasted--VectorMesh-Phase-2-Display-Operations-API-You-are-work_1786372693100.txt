# VectorMesh Phase 2 — Display Operations API

You are working on the existing **VectorMesh** application.

The objective of this phase is to extend the VectorMesh backend so that external operational clients — initially the **VectorMesh Multiview desktop application** — can securely discover projects, venues and screens, and request a safe, read-only monitoring URL for each screen.

This must be implemented as an extension of the existing VectorMesh backend and data model. Do not rebuild functionality that already exists. First inspect the current application architecture, database schema, authentication system, player model, screen model, project/event structure, venue/grouping structure and existing API routes.

The existing application already has physical display/player URLs similar to:

`https://vectormesh.4wallcloud.com?player=XXXXX`

where `XXXXX` is the unique code associated with a physical/signage player instance.

The new monitoring system must **not** simply reuse these player URLs externally. We need to introduce the concept of a separate **monitor session**.

---

# 1. Architectural Objective

VectorMesh should become the source of truth for:

- Projects / events
- Venues / locations / screen groups
- Screens
- Physical players
- Current online/offline status
- Screen metadata
- User access permissions
- Monitor sessions
- Future operational diagnostics

External clients such as VectorMesh Multiview should communicate with VectorMesh only through defined APIs.

The Multiview application must never connect directly to the VectorMesh database.

The desired architecture is:

VectorMesh database  
↓  
VectorMesh backend / Display Operations API  
↓  
VectorMesh Multiview desktop app  
↓  
Dynamic monitor views

---

# 2. Preserve the Existing Player Concept

A physical VectorMesh display/player currently identifies itself using a URL such as:

`https://vectormesh.4wallcloud.com?player=ABCDE`

This mechanism should continue to work exactly as it does now.

Do not break existing players.

The physical player should remain responsible for:

- display playback
- heartbeat/status reporting
- physical-device identity
- normal content delivery
- physical screen/player state

However, introduce a clear separation between:

### Physical Player Session

Represents the genuine deployed endpoint.

and

### Monitor Session

Represents an operator viewing what that screen should be displaying.

A monitor session must NOT:

- identify itself as the physical player
- overwrite the physical player's heartbeat
- affect online/offline status
- count as another physical device
- alter player health statistics
- perform administrative operations unless specifically authorised
- modify screen assignment
- modify content scheduling

It is fundamentally a viewing/operations session.

# 3. Add Display Operations API

Create a clean API namespace for operational clients.

Preferred namespace:

`/api/operations/`

Do not use this exact path if the existing VectorMesh API architecture has a more appropriate convention. Follow the current project's patterns where possible.

Implement the following capabilities.

# 4. Authentication

External operational clients must authenticate.

Use the existing VectorMesh user authentication system wherever possible.

Do not create a second independent user database.

Create or expose an API authentication mechanism suitable for the Electron Multiview desktop application.

Preferred behaviour:

`POST /api/operations/auth/login`

Request:

```json
{
  "email": "operator@example.com",
  "password": "..."
}
```

Response:

```json
{
  "accessToken": "...",
  "expiresAt": "...",
  "user": {
    "id": "...",
    "name": "...",
    "email": "...",
    "role": "..."
  }
}
```

If VectorMesh already uses secure session cookies, JWTs, refresh tokens or another authentication mechanism, reuse the existing design instead of unnecessarily introducing another authentication model.

Security is more important than following the example literally.

The API should support session expiry and revocation.

---

# 5. Permissions

Add permissions suitable for future operations tooling.

At minimum support:

- `operations.view`
- `operations.multiview`
- `operations.screen.read`
- `operations.diagnostics.read`

Prepare the architecture for later permissions such as:

- `operations.player.refresh`
- `operations.player.restart`
- `operations.player.reboot`
- `operations.logs.read`
- `operations.content.control`

Do not necessarily implement all future operations yet.

The important thing is to avoid hard-coding "admin only" logic throughout the API.

The API should be permission-driven.

Do NOT expose the physical player's secret or pairing credential unless absolutely necessary.

In particular, do not expose the current `?player=XXXXX` code directly to normal API clients if it can be avoided.

The desktop Multiview application should work using screen IDs and monitor sessions.

# 9. Monitor Session API

This is the most important part of Phase 2.

Create an API endpoint such as:

`POST /api/operations/screens/:screenId/monitor-session`

The endpoint should verify:

- authenticated user
- project access
- screen access
- `operations.multiview` permission

If allowed, create a temporary monitor session.

Example response:

```json
{
  "screenId": "screen-001",
  "monitorSessionId": "monitor-session-xyz",
  "monitorUrl": "https://vectormesh.4wallcloud.com/monitor/screen-001?token=SIGNED_TOKEN",
  "expiresAt": "2026-08-10T22:00:00Z"
}
```

The exact implementation may differ, but the important requirement is:

### A monitor URL must be separate from the physical player URL.

---

# 10. Monitor Token Requirements

Monitor URLs/tokens should:

- be securely generated
- be cryptographically unguessable
- be time-limited
- be revocable
- identify the user or client that requested them where practical
- identify the target screen
- grant read-only monitor access
- not grant normal player/device privileges

Consider token lifetimes somewhere in the region of a few hours, but make this configurable.

Do not embed sensitive user credentials into the URL.

A short-lived signed token is preferred.

---

# 11. Monitor Rendering Route

Create the corresponding monitor route.

For example:

`GET /monitor/:screenId?token=...`

This page should reproduce what that particular VectorMesh screen should display.

It should render using the same content/schedule/display logic as the physical player wherever possible.

Avoid duplicating the playback engine.

Ideally, both:

physical player

and

monitor viewer

should use a shared underlying rendering/content-selection service.

However:

### The monitor page must never behave like a physical player.

It must not:

- send player heartbeats as the real screen
- mark the screen online
- write physical health status
- overwrite player state
- claim the player identity
- affect analytics intended to represent physical displays

---

# 12. Monitor Mode Detection

Introduce a clear application concept such as:

`mode = player`

or

`mode = monitor`

Shared display-rendering code should be able to behave appropriately depending on the mode.

For example:

```text
PLAYER MODE
- normal playback
- physical heartbeat
- health reporting
- local player commands
- physical player identity

MONITOR MODE
- normal playback rendering
- NO physical heartbeat
- NO hardware reporting
- read-only screen representation
- optional operator overlay support
```

Do not simply fake a physical player in the database.

Monitor sessions should be first-class sessions.

# 21. Multiview App Intended Workflow

The eventual Electron application should be able to do the following:

1. Launch VectorMesh Multiview.
2. Log into VectorMesh.
3. Request available projects.
4. Operator selects a project.
5. Request venues/groups.
6. Operator selects a venue.
7. Request all screens in the venue.
8. Display screen names and status.
9. Request a monitor session for each screen.
10. Receive one temporary monitor URL per screen.
11. Dynamically create Electron WebContentsViews.
12. Load the returned monitor URLs.
13. Subscribe to live status changes.
14. Show health/status overlays.

The API you build now must make this workflow clean and straightforward.

# 22. Important Non-Goals

Do NOT:

- create duplicate screens for Multiview
- require users to manually pair monitor views
- make the Multiview application know the database schema
- turn monitor views into fake physical players
- expose player credentials unnecessarily
- change physical-player behaviour unless required for clean separation
- rewrite working VectorMesh systems without good reason
- build a second independent authentication system
- couple the API specifically to Electron

This should be a generic **Display Operations API**.

Electron Multiview is simply its first client.

# 27. Before Writing Code

Before implementing anything:

1. Inspect the current VectorMesh architecture.
2. Identify existing models for projects, screens, players and grouping.
3. Identify existing authentication and permissions.
4. Identify how the current `?player=XXXXX` route resolves a screen.
5. Identify where heartbeat/status is written.
6. Identify the current rendering/content selection logic.
7. Identify any existing API versioning.
8. Identify any existing WebSocket/realtime system.
9. Identify whether there is already a reusable service layer between routes and database code.

Then produce a short implementation plan showing:

- existing components that will be reused
- database changes required
- new API routes
- security model
- monitor/player separation approach
- files/modules that will change

After this analysis, proceed with implementation.

Do not create unnecessary parallel systems if VectorMesh already has suitable infrastructure.

The priority is to extend the existing architecture cleanly and safely.

# Product Principle

The goal is:

**If a screen already exists in VectorMesh, an authorised operator should be able to see it in Multiview without creating another screen, pairing another player or manually entering another player code.**

VectorMesh already knows the project, venue, screen and content.

The Multiview client should simply ask VectorMesh for access to view it.

Build Phase 2 around that principle.
