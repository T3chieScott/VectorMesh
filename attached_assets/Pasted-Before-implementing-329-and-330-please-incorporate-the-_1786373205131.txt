Before implementing #329 and #330, please incorporate the following architectural refinements:

1. Treat `projects`, `venues`, and `screens` as stable Operations API concepts even where they currently map internally to `clients`, `screen_groups`, and existing screen/player models. Do not leak unnecessary database terminology into the public API contract.

2. Prefer extending an existing scopes/permissions system or using a small relational operations-permission model rather than storing an unstructured JSON permission array on tokens, unless the existing architecture clearly makes token scopes the correct choice.

3. `monitorUrl` returned by the monitor-session endpoint must be a complete absolute HTTPS URL so external clients do not need to know or construct the VectorMesh server base URL.

4. Add an expired monitor-session retention/cleanup strategy. Sessions may remain for audit purposes for a defined period, but expired rows must not accumulate indefinitely.

5. Monitor mode must be fail-safe. Avoid scattering individual `if (!isMonitorMode)` checks throughout `player.tsx` wherever possible. Introduce a central runtime capability/policy abstraction so that monitor sessions explicitly cannot:
   - heartbeat
   - report hardware/video health
   - pair
   - persist physical device identity
   - alter physical player state
   - receive future player-only commands unless deliberately enabled

6. New physical-player functionality added later should default to disabled in monitor mode unless explicitly declared safe.

7. Monitor-session validation should use constant-time-safe token comparison semantics where applicable, and raw monitor tokens must never appear in logs, analytics, audit payloads or error messages.

8. Keep #329 completely non-invasive to existing player behaviour. Do not make preparatory changes to the player runtime until #330 unless strictly necessary.

9. At the end of #329, provide the exact API contract that the Electron Multiview client can begin integrating against, including example JSON responses and authentication behaviour.

10. At the end of #330, demonstrate the critical invariant with an automated test:
   loading the monitor URL repeatedly must leave the physical screen's `lastSeen`, online state, device identity and heartbeat records unchanged.
