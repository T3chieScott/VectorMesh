# VectorMesh Multiview — Investigate and Fix Monitor Bootstrap Rate Limiting

We have reproduced a deterministic production issue in the VectorMesh Multiview workflow.

## Confirmed client-side evidence

The Electron client successfully does:

1. `POST /api/operations/screens/:screenId/monitor-session`
2. receives `201` with a valid `monitorSessionId`, `expiresAt`, and bootstrap `monitorUrl`

But when several screens are loaded quickly, the next request:

`GET /monitor-bootstrap/:screenId?token=...`

starts returning:

`HTTP 429 Too Many Requests`

Example diagnostics:

- monitor session creation succeeds
- bootstrap request starts
- `/monitor-bootstrap/<screenId>` returns `429`
- no `302` redirect occurs
- browser remains on `/monitor-bootstrap/<screenId>`
- the canonical `/monitor/:screenId` page never loads

This is why the Electron tiles appear to show "UNAUTHORIZED" / failed monitor sessions during rapid project switching or when many screens are opened at once.

The client-side session race has already been fixed. The remaining reproducible failure is the 429 on the bootstrap route.

Do not modify the Electron app in this task.

---

## Objective

Identify the exact rate limiter applying to:

`GET /monitor-bootstrap/:screenId`

and change the backend policy so normal Multiview startup with many legitimate monitor sessions does not get throttled.

Do not simply remove rate limiting globally.

Do not weaken monitor-token validation.

---

## Investigation first

Before changing code, trace the actual middleware chain for:

`GET /monitor-bootstrap/:screenId`

Report:

1. Which rate limiter returns the 429.
2. Where it is defined.
3. Whether it is:
   - global
   - API-wide
   - auth/login limiter
   - route-specific
   - proxy/nginx-level
4. Current:
   - window duration
   - max requests
   - keying strategy
   - skip/success behaviour
5. Whether successful and invalid bootstrap requests are counted the same way.
6. Whether `/api/operations/screens/:screenId/monitor-session` has a separate limiter.
7. Whether nginx/Plesk contributes any additional throttling.

Do not guess from filenames; trace the actual request path.

---

## Expected legitimate behaviour

The Multiview client may legitimately open:

- 8 screens
- 16 screens
- 25 screens
- potentially 50 screens

during one project load.

For each screen, the client creates a monitor session and immediately loads one single-use bootstrap URL.

This is normal traffic, not abuse.

A valid startup burst must not return 429.

---

## Security context

The bootstrap route already has strong controls:

- 32-byte cryptographically random bootstrap token
- token stored hashed at rest
- token expiry
- token is single-use
- screen/session binding
- server-side monitor-session validation
- HttpOnly Secure session cookie after exchange

Do not change these controls.

Rate limiting should remain as defence-in-depth against brute-force / invalid-token abuse.

---

## Preferred design

Use a dedicated limiter for `/monitor-bootstrap/:screenId` rather than inheriting a low generic auth/login/global limiter.

The exact numbers should be based on the current backend architecture, but design for normal bursts of at least 25–50 legitimate bootstrap exchanges.

For example, a burst allowance in the region of 100 successful bootstrap attempts per minute per source IP may be reasonable, but do not blindly use this number. Inspect the existing limiter and choose a safe production policy.

Where practical:

- valid single-use bootstrap exchanges should not be penalised by an overly aggressive login-style limiter
- repeated invalid token attempts should still be rate-limited
- successful Multiview project loads must complete without 429s

If the limiter library supports differentiated handling for failed vs successful requests, consider that design.

---

## Important proxy/IP check

VectorMesh runs behind nginx/Plesk.

Verify that the application sees the real client IP correctly.

Check Express `trust proxy` configuration and limiter key generation.

Do not accidentally create a limiter where all users share one proxy IP and therefore consume one global bucket.

If the current limiter is effectively keying every request to localhost/nginx rather than the real remote IP, report that explicitly.

---

## Tests

Add automated tests covering at least:

1. A normal burst of 25 valid monitor bootstrap exchanges succeeds.
2. A normal burst of 50 valid monitor bootstrap exchanges succeeds if that is within the chosen production design target.
3. Clearly excessive invalid bootstrap requests are still rate-limited.
4. Invalid bootstrap token still returns the correct authentication failure.
5. Expired token remains rejected.
6. Revoked token remains rejected.
7. Bootstrap token remains single-use.
8. Existing monitor-session cookie/session security remains unchanged.
9. Existing monitor invariant tests still pass.
10. No change to physical player heartbeat/status behaviour.
11. Normal Operations API token rate limiting remains unchanged.
12. Project switching / multiple sequential bursts does not unexpectedly exhaust a long-lived shared limiter bucket.

---

## Observability

Improve safe diagnostics around bootstrap throttling.

When a bootstrap request is rate-limited, log only safe metadata such as:

- route
- timestamp
- resolved client IP / limiter key
- limiter name
- retry-after / reset information if available

Never log:

- raw bootstrap token
- monitor session secret
- API token
- cookie secret

Return a useful `Retry-After` header where supported.
